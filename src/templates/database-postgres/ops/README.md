# Aprovisionamiento de PostgreSQL

1. Un operador prepara una base dedicada. Desde el backend, ejecuta como administrador `psql -X -d NOMBRE_BD -v target=NOMBRE_BD -f ops/provision.sql`. Repetir el SQL conserva las contraseñas y rechaza roles incompatibles o asignados a otra base.
2. Conéctate mediante una sesión administrativa protegida y asigna secretos distintos con `SET password_encryption = 'scram-sha-256';` y los prompts de `\password table_owner` y `\password app_exec`, o mediante las herramientas equivalentes del proveedor. Usa ese paso para credenciales nuevas, nunca para reemplazar contraseñas existentes por defecto.
3. Ejecuta `npm run db:migrate` con `MIGRATION_DATABASE_URL` de `table_owner` solo en el entorno de esa orden. Express recibe únicamente `DATABASE_URL` de `app_exec`.
4. Versiona en tus migraciones los permisos precisos para cada tabla nueva. Por ejemplo, si una ruta solo lee e inserta artículos, concede `GRANT SELECT, INSERT ON public.articulos TO app_exec;` y, si su identificador usa una secuencia, `GRANT USAGE ON SEQUENCE public.articulos_id_seq TO app_exec;`. Amplía las concesiones únicamente cuando la funcionalidad lo requiera. No se conceden privilegios DML automáticos a todas las tablas.

El aprovisionamiento espera que los objetos de `public` y `drizzle` que administra la aplicación pertenezcan a `table_owner`. En despliegues con datos, roles u objetos previos, revisa propiedad, ACL, membresías y dependencias con el DBA antes de aplicar el SQL. Usa un clúster dedicado si colisionan los nombres de rol. No se transfieren objetos, adoptan roles ni rotan secretos automáticamente. Revisa también las rutinas y triggers que operen con privilegios de su propietario; las comprobaciones de arranque del rol no sustituyen esa revisión.

El contrato anterior de PostgreSQL base, que aceptaba una sola credencial para migrar y ejecutar, no es compatible con estas plantillas. Brixa genera proyectos nuevos; una transición de un proyecto existente requiere planificación y revisión operativa.
