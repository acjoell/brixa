# PostgreSQL 17 para Auth

El aprovisionamiento afecta los permisos de conexión y creación de la base elegida y de su esquema public. Usa una base dedicada y un clúster donde estos nombres de rol estén reservados para este proyecto. Los roles PostgreSQL son globales al clúster.

1. Como administrador de la base con autorización para crear roles, ejecuta desde el backend `psql -X -d NOMBRE_BD -v target=NOMBRE_BD -f ops/provision.sql`. En Compose inicia primero `docker compose up -d postgres`. Desde la raíz ejecuta `docker compose exec -T postgres psql -X -U postgres -d app -v target=app < ops/provision.sql` (fullstack: usa `backend/ops/provision.sql`). Sustituye los nombres si configuraste POSTGRES_USER o POSTGRES_DB. El script es transaccional y repetirlo conserva las contraseñas.
2. En una sesión interactiva psql del administrador (Compose: `docker compose exec postgres psql -X -U postgres -d app`), usa `SET password_encryption = 'scram-sha-256';`, luego los comandos separados `\password table_owner` y `\password app_exec`. Asigna secretos distintos mediante los prompts o usa el mecanismo de credenciales del proveedor. Configura autenticación por contraseña sobre una conexión protegida.
3. Inyecta MIGRATION_DATABASE_URL solo en los procesos puntuales de migración y bootstrap documentados en el README. Ejecuta las migraciones antes del bootstrap y de arrancar Express. DATABASE_URL utiliza app_exec. El administrador conserva acceso para operaciones y revisión del historial.

## Instalaciones con datos o roles previos

Detén los escritores, toma y verifica una copia de seguridad e inventaría propietarios, ACL, membresías y privilegios por defecto (psql: `\l+`, `\dn+`, `\dt+ public.*`, `\d+ drizzle.__drizzle_migrations`, `\dp`, `\ddp`, `\du+`). El script indica los objetos Auth con propietario incompatible y rechaza roles que no llevan su marca para esta base. No reemplaza credenciales ni transfiere propiedad. En un proveedor administrado el operador puede provisionar identidades y permisos equivalentes mediante sus herramientas.

Si la base es compartida o hay colisiones de rol, prepara un clúster dedicado y restaura una copia verificable. Para una transición en la base dedicada, el DBA debe aprobar individualmente la adopción de los roles, la propiedad por table_owner de users, sessions, audit_log_system y del esquema y objetos de historial Drizzle (incluida la secuencia), así como los permisos de los demás consumidores antes de restringir PUBLIC. Evita REASSIGN OWNED global. Para adoptar roles existentes mediante el script, aplica su comentario de identificación únicamente tras verificar que pertenecen exclusivamente a este despliegue. Comprueba también funciones SECURITY DEFINER, triggers y grants por columna personalizados. Conserva el journal y sus filas aplicadas, compara los datos antes y después, ejecuta db:migrate y comprueba el arranque con la credencial runtime.

Si 0002 informa una ACL residual, inspecciona la columna con `\dp public.audit_log_system`, identifica el otorgante y retira la concesión con esa identidad antes de repetir db:migrate. Una migración ya aplicada no vuelve a ejecutarse. El control de arranque sigue comprobando los permisos efectivos.

Antes de habilitar escritores, el DBA debe revisar las rutinas SECURITY DEFINER accesibles (incluido EXECUTE de PUBLIC), vistas y sus reglas, y funciones de triggers de las tablas Auth. El arranque señala rutinas con autoridad directa sobre el historial, triggers asociados y vistas modificables dependientes del historial. Es una comprobación conservadora del catálogo. Revisa manualmente llamadas encadenadas, SQL dinámico, reglas personalizadas, extensiones y cambios administrativos posteriores. Retira el acceso o el objeto incompatible tras revisar sus consumidores y vuelve a comprobar el arranque.
